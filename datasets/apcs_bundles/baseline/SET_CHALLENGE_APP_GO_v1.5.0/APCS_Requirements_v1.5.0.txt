Legend
------
[MUST]   Hard requirement. Failure to satisfy blocks promotion.
[SHOULD] Recommended. A miss yields a soft warning, not a HOLD.
[COULD]  Nice-to-have. Tracked for future iterations.

--------------------------------------------------------------------
1. Agent decision engines
--------------------------------------------------------------------

REQ-CHA-001 [MUST]    Agent 4 (Release Readiness) shall ingest an APCS
                      document bundle (Requirements, Test Procedure,
                      Module Version Inventory, Emails, VDD) and
                      produce a deterministic GO / HOLD decision that
                      cannot be overridden by the optional LLM summary.

REQ-CHA-002 [MUST]    Agent 5 (Test Evidence) shall ingest the
                      structured Phase 5 dataset (requirements_master,
                      test_cases_master, traceability_matrix,
                      test_execution_results, defect_register) and
                      raise HOLD on any unresolved hard gate (open
                      critical defect, missing traceability, failed
                      execution).

REQ-CHA-003 [MUST]    The Brain orchestrator shall block Phase 5 when
                      Phase 4 ends in HOLD, unless the operator
                      explicitly enables the override flag.

--------------------------------------------------------------------
2. CI / CD pipeline integration
--------------------------------------------------------------------

REQ-CHA-004 [MUST]    The GitHub Actions workflow shall execute
                      Agent 4 (analyze-pre-test) on every push and
                      pull_request against `main`, and Agent 5
                      (analyze-pre-prod) only after a successful
                      build on push or release events.

REQ-CHA-005 [MUST]    Promotion to TEST shall be gated by the
                      `hitachi-test-approval` environment with
                      Required Reviewers; promotion to PROD shall be
                      gated by `hitachi-prod-approval`.

REQ-CHA-006 [MUST]    Each pipeline run shall publish the Agent 4 and
                      Agent 5 reports as artifacts named
                      `ci-analysis-pre-test` and `ci-analysis-pre-prod`,
                      each containing a `ci_report.json` payload.

REQ-CHA-007 [SHOULD]  The pipeline shall publish a `ci-stage-results`
                      artifact with the build/test summary so the
                      dashboard can render PASS/FAIL stage cards.

--------------------------------------------------------------------
3. Dashboard / CI bridge
--------------------------------------------------------------------

REQ-CHA-008 [MUST]    The backend shall expose the following CI bridge
                      endpoints under `/ci`:
                        - GET  /ci/status
                        - GET  /ci/runs
                        - GET  /ci/runs/{id}
                        - GET  /ci/runs/{id}/pending-deployments
                        - POST /ci/approve
                        - POST /ci/dispatch

REQ-CHA-009 [MUST]    The CI bridge shall degrade gracefully when
                      `CI_BRIDGE_REPO` or `CI_BRIDGE_TOKEN` are unset,
                      returning `configured: false` instead of failing.

REQ-CHA-010 [MUST]    Artifact downloads shall strip the Authorization
                      header on cross-host redirects to GitHub blob
                      storage (S3 / Azure) to avoid 400 conflicts.

REQ-CHA-011 [MUST]    The dashboard shall expose an "CI / CD Pipeline"
                      tab that lists the most recent runs and shows
                      the parsed Agent 4 / Agent 5 reports, the stage
                      results, and any pending deployment for the
                      selected run.

REQ-CHA-012 [MUST]    The dashboard shall allow approving or rejecting
                      a pending deployment directly when the bound
                      token has Actions:write permission.

REQ-CHA-013 [SHOULD]  When any run is non-terminal (queued, in_progress,
                      waiting), the dashboard shall auto-refresh the
                      run list (20s) and the selected run details
                      (15s) and surface a "Live" indicator in the
                      header.

REQ-CHA-014 [SHOULD]  Evidence references rendered in the dashboard
                      shall include a relative file path and, when
                      available, a textual snippet excerpt.

--------------------------------------------------------------------
4. Deployment & operations
--------------------------------------------------------------------

REQ-CHA-015 [MUST]    Container images deployed to TEST and PROD
                      shall be pinned by digest, not by mutable tag.

REQ-CHA-016 [MUST]    The Helm chart shall mount `OPENROUTER_API_KEY`
                      and `CI_BRIDGE_TOKEN` from the Kubernetes secret
                      `challenge-app-secrets`. The chart shall fail
                      fast if the secret keys are missing.

REQ-CHA-017 [SHOULD]  Image build, registry push and GitOps repo
                      update shall be performed by the CI pipeline,
                      not manually.

REQ-CHA-018 [COULD]   The dashboard shall offer a "Re-run" button
                      backed by `POST /ci/dispatch` for manually
                      triggering the pipeline on the active branch.

--------------------------------------------------------------------
5. Documentation & traceability
--------------------------------------------------------------------

REQ-CHA-019 [MUST]    Each requirement (REQ-CHA-*) shall be linked to
                      at least one test case (TC-CHA-*) in the
                      traceability matrix. Orphan requirements raise
                      Agent 5 HOLD.

REQ-CHA-020 [SHOULD]  TEST promotion requires no open critical defect
                      and no unresolved blocker email in the release
                      correspondence (`APCS_Emails.txt`).
