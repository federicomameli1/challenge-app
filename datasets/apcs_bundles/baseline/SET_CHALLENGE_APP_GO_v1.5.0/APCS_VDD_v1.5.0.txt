Scope of change
---------------
- New backend module `backend.ci_bridge` providing read + write
  access to GitHub Actions runs, artifacts and pending deployments.
- New "CI / CD Pipeline" tab on the dashboard, with:
    * a list of recent runs;
    * Agent 4 / Agent 5 / Stage Results cards parsed from the run
      artifacts;
    * an "Awaiting approval" card that approves or rejects the
      pending deployment directly from the dashboard;
    * an auto-refresh loop and a "Live" indicator while any run is
      non-terminal.
- New environment variables consumed by the backend at startup:
  `CI_BRIDGE_REPO`, `CI_BRIDGE_TOKEN`, `CI_BRIDGE_BRANCH` (optional).
- Helm chart updated to wire `CI_BRIDGE_TOKEN` from the existing
  `challenge-app-secrets` Secret.
- CI workflow updated so that `analyze-pre-prod` runs on `push` and
  `release` events, gating both promotions through the
  `hitachi-test-approval` and `hitachi-prod-approval` environments.

Out of scope
------------
- Real LLM-driven document analysis (planned for a later iteration).
- Real GitHub PR ingestion as Agent 4 input (the pipeline still
  feeds Agent 4 with the APCS bundle in `docs/release/`).
- VDD / nulla osta PDF generation.
- Workflow re-dispatch from the dashboard (REQ-CHA-018, COULD).

Deliverables
------------
- Container image (multi-arch, scanned, no critical CVE).
- Helm chart 0.2.0.
- APCS release bundle in `docs/release/` (this folder).
- CI workflow `.github/workflows/ci.yml`.

Known limitations
-----------------
- `current_user_can_approve` reflects the permissions of the token
  bound on the backend, not of the dashboard end-user. When the
  token lacks Actions:write the dashboard falls back to "approve
  via GitHub directly" instead of showing the Approve / Reject
  buttons.
- The auto-refresh loop is global per session; there is no
  per-tab pause yet.
